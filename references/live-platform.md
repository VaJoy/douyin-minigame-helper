# 多端与流量场景

> **适用**：推荐流直玩、直播、小游戏站、PC 端、鸿蒙端。
> **源文档**：`docs/develop/guide/open-ability/`（feed / mini-game-station / pc-game / harmony）、`docs/operation/` 相关。
> **关联**：广告与支付在各自文件里；包体与性能见 `performance.md`。

## 推荐流直玩（重点）

抖音信息流里直接出游戏，用户点开即玩（容器预加载），是目前最大的免费流量入口之一。分两个版本：

| 版本 | 目标 | 特点 |
|---|---|---|
| **获客版** | 拉新 | 面向大盘游戏偏好投放，接入流程约 2-5 天 |
| **复访版** | 召回老用户 | 面向已玩过的用户，配合侧边栏复访 |

### 接入要点

1. **场景值判断**：从推荐流进入时 `tt.getLaunchOptionsSync().scene === 3041`，业务上要区分该来源做首屏加速与新手引导。
2. **上报加载完成**：必须调用加载完成上报接口，否则平台无法计算真实激活，影响后续流量分配。
3. **监听进入/退出**：用「预览流进入/退出小游戏事件」判断用户是否真实启动，避免把预加载当活跃。
4. **设计规范**：竖屏/横屏各有规范（首屏信息密度、可玩时长、加载时长），提报方案时要过审。

```js
const { scene } = tt.getLaunchOptionsSync();
if (scene === 3041) {
  // 推荐流直玩：优先出首屏、缩短加载、埋点上报
}
```

### 常见坑

- 首屏太重导致「预加载完成但进不去」，会被判低质，流量下滑。
- 不上报加载完成 → 平台侧数据缺失，后续拿不到量。
- 场景值不区分 → 新手引导/存档逻辑错乱（直玩用户往往没有历史存档）。

## 直播场景

- **直播间小摇杆**：主播挂载小游戏，观众从直播间进入。
- **直播即看即玩**：在直播间内直接运行，见 `instant-play-introduce.md`。
- 直播场景的账号体系与主端不同，需处理「直播场景扫码切换账号」（有专门接入指南）。
- 互动性强，首屏要极快，且要能处理「主播操作、观众围观」的非对称输入。

## 小游戏站

平台内的游戏聚合页，用户可从小游戏站直接进入。

- 接入方式见 `mini-game-station/tt-minigame-access.md`（`tt.navigateToMiniProgram` 等）。
- 上架需要单独提报，有独立的审核标准（游戏站审核规则）。
- 适合做「游戏矩阵」互推，配合互推资源位。

## PC 端小游戏

- 抖音 PC 客户端可运行小游戏，入口与移动端不同。
- **支付只支持钻石支付**，`platform: 'windows'`。
- 键鼠适配是重点：需要把触摸操作映射到鼠标/键盘（`tt.onMouseDown`、`onKeyDown` 等）。
- 有专门的 PC 优化建议（分辨率、窗口、性能档位），见 `pc-game/pc-games-optimization.md`。

## 鸿蒙端（HarmonyOS）

- `tt.getSystemInfoSync().platform === 'openHarmony'`。
- 兼容性差异见 `harmony/harmony-compatibility.md`：部分 API 在鸿蒙上不支持或行为不同，上线前要单独回归。
- 鸿蒙端的支付、广告能力支持情况与安卓不完全一致，需实测。

## 多端适配的通用建议

1. **能力探测优先于平台判断**：用 `tt.canIUse` 判断能力，而不是 `if (platform === 'ios')` 硬编码分支。
2. **输入抽象一层**：触摸/鼠标/键盘统一成一套输入事件，业务层不感知来源。
3. **安全区适配**：`tt.getSystemInfoSync().safeArea`，刘海屏、折叠屏都要留边。
4. **按端分档**：PC 大屏不等于高性能，仍要按 `deviceScore` 做画质分级。
